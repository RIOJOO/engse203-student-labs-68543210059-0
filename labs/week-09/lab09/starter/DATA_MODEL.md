# DATA_MODEL.md — การออกแบบฐานข้อมูล Campus Service Request

## 1. ภาพรวม

```
┌─────────────────────┐          ┌──────────────────────────┐
│ users               │          │ requests                 │
├─────────────────────┤          ├──────────────────────────┤
│ id          (PK)    │◄────────┐│ id             (PK)      │
│ name                │         └│ requester_id   (FK)      │
│ department          │          │ request_type             │
│ email       (UNIQUE)│          │ location · details       │
└─────────────────────┘          │ priority · status        │
                                 │ created_at               │
                                 └──────────────────────────┘
```

ความสัมพันธ์เป็นแบบ **หนึ่งต่อหลาย (one-to-many)** — ผู้ใช้ 1 คนแจ้งได้หลายคำร้อง แต่คำร้อง 1 รายการมีผู้แจ้งได้คนเดียว ฝั่ง "หลาย" (`requests`) จึงเป็นฝั่งที่เก็บ Foreign Key (`requester_id`) ชี้ไปที่ `users.id`

---

## 2. ทำไมต้องแยกเป็น 2 ตาราง

ตอน Week 06–07 เราเก็บ `requesterName` เป็นข้อความในทุกคำร้อง ถ้าสมชายแจ้ง 3 เรื่อง ชื่อ "สมชาย ใจดี" จะถูกเก็บซ้ำ 3 ที่ แล้วถ้าสมชายเปลี่ยนชื่อ **ต้องแก้ 3 ที่ (หรือเท่ากับจำนวนคำร้องของเขา)** แต่หลังแยกตาราง ชื่อเก็บอยู่ที่เดียวใน `users` แก้ครั้งเดียวทุกคำร้องก็เห็นชื่อใหม่ทันที

ปัญหาของการเก็บชื่อซ้ำในทุกคำร้อง

1. **ข้อมูลซ้ำซ้อน** — ชื่อ ภาควิชา และอีเมลของคนเดียวกันถูกเก็บซ้ำทุกแถว เปลืองพื้นที่และยิ่งคำร้องเยอะยิ่งซ้ำมาก
2. **แก้ไม่ครบ (update anomaly)** — ถ้าแก้ชื่อเพียงบางแถวและพลาดบางแถว ข้อมูลของคนเดียวกันจะขัดแย้งกันเอง เช่น คำร้องหนึ่งเป็น "สมชาย" อีกคำร้องเป็น "สมชาย ใจดี" และไม่มีทางรู้ว่าอันไหนถูก
3. **เก็บคนที่ยังไม่เคยแจ้งไม่ได้** — ถ้าชื่อผู้ใช้อยู่ในตารางคำร้องเท่านั้น คนที่ยังไม่เคยแจ้งจะไม่มีที่อยู่เลย (เช่น "วรินทร์ มานะ" ในฐานข้อมูลนี้ที่ยังไม่มีคำร้อง) และถ้าลบคำร้องสุดท้ายของใครก็ตาม ข้อมูลของคนนั้นจะหายไปด้วย
4. **พิมพ์ผิดแล้วไม่มีใครรู้** — "สมชาย" กับ "สมชาย " (มีช่องว่างท้าย) ถูกนับเป็นคนละคน ทำให้ค้นหรือนับจำนวนผิด แต่ถ้าใช้ `requester_id` เป็นตัวเลขที่ชี้ไปหา `users` และเปิด Foreign Key ไว้ ฐานข้อมูลจะปฏิเสธ id ที่ไม่มีจริงให้เอง

แนวคิดสรุปคือ **เก็บข้อมูลแต่ละอย่างไว้ที่เดียว แล้วเชื่อมถึงกันด้วยความสัมพันธ์**

## 3. รายละเอียดตาราง

### ตาราง `users`

| คอลัมน์ | ชนิด | ข้อกำหนด | เหตุผลที่เลือกแบบนั้น |
|---|---|---|---|
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | ฐานข้อมูลรันเลขให้เอง ไม่ซ้ำ และไม่เปลี่ยนแม้ผู้ใช้เปลี่ยนชื่อหรืออีเมล จึงเหมาะเป็นตัวอ้างอิง |
| `name` | TEXT | NOT NULL | คนที่ไม่มีชื่อไม่มีความหมายในระบบ และต้องใช้แสดงในรายการคำร้อง |
| `department` | TEXT | NOT NULL | ใช้กรองคำร้องตามภาควิชา (query ข้อ ⑥) จึงต้องมีค่าเสมอ |
| `email` | TEXT | NOT NULL, UNIQUE | อีเมลระบุตัวคนได้ จึงห้ามซ้ำ ป้องกันการสร้างบัญชีสองบัญชีให้คนเดียวกัน |

### ตาราง `requests`

| คอลัมน์ | ชนิด | ข้อกำหนด | เหตุผลที่เลือกแบบนั้น |
|---|---|---|---|
| `id` | TEXT | PRIMARY KEY | ใช้รหัสอ่านง่ายแบบ `REQ-001` ที่ผู้ใช้เห็นและอ้างถึงได้ ตรงกับรูปแบบที่ API เดิมใช้ |
| `requester_id` | INTEGER | NOT NULL, FOREIGN KEY → `users(id)` | ทุกคำร้องต้องมีผู้แจ้งที่มีอยู่จริง ชนิดต้องตรงกับ `users.id` |
| `request_type` | TEXT | NOT NULL, CHECK IN (4 ค่า) | จำกัดประเภทให้เป็นค่าที่ระบบรู้จัก กันพิมพ์ผิดหรือสร้างประเภทมั่ว |
| `location` | TEXT | NOT NULL | ช่างต้องรู้ว่าไปที่ไหน ถ้าว่างคำร้องก็ใช้งานไม่ได้ |
| `details` | TEXT | NOT NULL | คำร้องที่ไม่มีรายละเอียดทำให้ผู้รับเรื่องไม่รู้ว่าต้องทำอะไร |
| `priority` | TEXT | NOT NULL, DEFAULT 'normal', CHECK IN ('normal','urgent') | ส่วนใหญ่เป็นเรื่องทั่วไป จึงตั้งค่าเริ่มต้นเป็น normal และจำกัดไว้ 2 ระดับ |
| `status` | TEXT | NOT NULL, DEFAULT 'pending', CHECK IN ('pending','in-progress','completed') | คำร้องใหม่ต้องเริ่มที่ pending เสมอ และมีได้แค่ 3 สถานะตามกระบวนการ |
| `created_at` | TEXT | NOT NULL, DEFAULT (datetime('now','localtime')) | บันทึกเวลาอัตโนมัติ ไม่ต้องพึ่งให้ผู้เรียกส่งมา และใช้เรียงคำร้องล่าสุดได้ |

## 4. เหตุผลของการเลือกชนิดและข้อกำหนด

**ทำไม `users.id` เป็น INTEGER แต่ `requests.id` เป็น TEXT**

`users.id` เป็นรหัสภายในที่คนไม่ต้องอ่าน ให้ฐานข้อมูลรันเลขอัตโนมัติ (AUTOINCREMENT) ได้เลย ส่วน `requests.id` เป็นรหัสที่ผู้ใช้เห็นและพูดถึงกัน เช่น "ขอตรวจ REQ-004" รูปแบบ `REQ-001` จึงอ่านง่ายกว่าเลข 4 และตรงกับข้อมูลที่ API ใน Week 06–07 ใช้อยู่แล้ว จึงไม่ต้องแปลงรหัสตอนต่อกับ React

**ทำไมต้องมี CHECK constraint ทั้งที่ API ก็ตรวจข้อมูลอยู่แล้ว**

เพราะ API ไม่ใช่ทางเดียวที่ข้อมูลจะเข้าฐานข้อมูล ยังมีสคริปต์ เครื่องมือ SQL ที่เปิดตรง หรือโค้ดของคนอื่นที่อาจลืมตรวจ CHECK ทำให้ฐานข้อมูลเป็นด่านสุดท้ายที่ปฏิเสธค่าผิดได้เสมอ (เช่น `status = 'ยกเลิก'`) ไม่ว่าข้อมูลจะมาจากทางไหน และถ้า API มีบั๊กก็ยังไม่มีข้อมูลเสียหลุดเข้ามา ตรวจสองชั้นดีกว่าชั้นเดียว

## 5. ตัวอย่างการใช้ JOIN

```sql
SELECT r.id,
       u.name AS requesterName,
       r.request_type,
       r.status
FROM requests r
JOIN users u ON u.id = r.requester_id
ORDER BY r.id
LIMIT 4;
```

| id | requesterName | request_type | status |
|---|---|---|---|
| REQ-001 | สมชาย ใจดี | แจ้งซ่อม | pending |
| REQ-002 | สุภาวดี รักเรียน | บริการบัญชีผู้ใช้ | in-progress |
| REQ-003 | ธนกฤต ตั้งใจ | ขอใช้อุปกรณ์ | completed |
| REQ-004 | สมชาย ใจดี | แจ้งซ่อม | pending |

## 6. ข้อสังเกตสำหรับสัปดาห์ที่ 10

```
-- ผลของ JOIN
REQ-001 | สมชาย ใจดี | pending

-- ข้อมูลที่ API ส่งให้ React (Week 07)
{ "id": "REQ-001", "requesterName": "สมชาย ใจดี", "status": "pending" }
```

สิ่งที่สังเกตเห็นคือ **ข้อมูลที่ได้จาก JOIN มีเนื้อหาเหมือนกับที่ API ส่งให้ React เกือบทุกอย่าง** เพียงแต่ชื่อผู้แจ้งมาจากตาราง `users` ไม่ได้ถูกเก็บซ้ำในทุกคำร้อง ผมจึงตั้งชื่อคอลัมน์ผลลัพธ์เป็น `requesterName` เพื่อให้ตรงกับ API เดิม ฝั่ง React จะไม่ต้องแก้อะไร

อีกข้อคือรูปแบบข้อมูลในฐานข้อมูลไม่จำเป็นต้องเหมือนรูปแบบที่ API ส่งออกเสมอไป (เช่น คอลัมน์เป็น `request_type` แบบ snake_case แต่ API ส่งเป็น camelCase) การแปลงระหว่างสองรูปแบบนี้จะเป็นหน้าที่ของชั้น service ในสัปดาห์ที่ 10

## ผลการทดสอบ Constraint (CP25)

ทดสอบโดยเปิด `PRAGMA foreign_keys = ON` แล้วลอง INSERT ข้อมูลที่ผิด ทั้ง 5 แบบถูกปฏิเสธตามที่ควร

### ① Foreign Key

```sql
INSERT INTO requests (id, requester_id, request_type, location, details)
VALUES ('REQ-TEST', 99999, 'แจ้งซ่อม', 'ห้องทดสอบ', 'ทดสอบระบบ');
```

**ผลที่ได้** `FOREIGN KEY constraint failed` ✓ ถูกปฏิเสธตามที่ควร

### ② CHECK

```sql
INSERT INTO requests (id, requester_id, request_type, location, details, status)
VALUES ('REQ-TEST', 1, 'แจ้งซ่อม', 'ห้องทดสอบ', 'ทดสอบระบบ', 'ยกเลิก');
```

**ผลที่ได้** `CHECK constraint failed: status IN ('pending','in-progress','completed')` ✓ ถูกปฏิเสธตามที่ควร

### ③ UNIQUE (อีเมลซ้ำ)

```sql
INSERT INTO users (name, department, email)
VALUES ('ทดสอบ อีเมลซ้ำ', 'วิศวกรรมไฟฟ้า', 'somchai@rmutl.ac.th');
```

**ผลที่ได้** `UNIQUE constraint failed: users.email` ✓ ถูกปฏิเสธตามที่ควร

### ④ PRIMARY KEY ซ้ำ

```sql
INSERT INTO requests (id, requester_id, request_type, location, details)
VALUES ('REQ-001', 1, 'แจ้งซ่อม', 'ห้องทดสอบ', 'ทดสอบ id ซ้ำ');
```

**ผลที่ได้** `UNIQUE constraint failed: requests.id` ✓ ถูกปฏิเสธตามที่ควร

### ⑤ NOT NULL

```sql
INSERT INTO requests (id, requester_id, request_type, details)
VALUES ('REQ-TEST', 1, 'แจ้งซ่อม', 'ทดสอบไม่ระบุ location');
```

**ผลที่ได้** `NOT NULL constraint failed: requests.location` ✓ ถูกปฏิเสธตามที่ควร
